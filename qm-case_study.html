QuenchMap

PHP · MySQL · Bootstrap · Google Maps · Role-Based Access · Location Data

Case Study

Integrating geographic visualization, community-generated data, administrative control, and role-based web access.

Problem Objective Users Features Map Reporting Database Access Administration Architecture Workflow Testing Outcome Documentation

The Problem

Information about publicly accessible drinking-water sources is often fragmented, incomplete, or difficult to locate. A source may be known only locally, while visitors and other users have no centralized way to discover it.

A simple map is not sufficient when the information must also be updated, expanded, reviewed, searched, and managed. A useful system needs geographic visualization, community participation, structured data storage, and administrative control.

The challenge was to design a platform where public users can access practical location information while registered users contribute new records and administrators preserve the structure and reliability of the system.

Project Motivation

QuenchMap was developed as a centralized, community-oriented information system that connects physical locations with structured web data and controlled user participation.

Project Objective

The objective was to build a full-stack web application that allows users to discover, search, report, and manage public drinking-water sources through an interactive map.

The application was designed around three access levels: guest, registered user, and administrator. Each role receives only the functions required for its purpose.

The system combines a responsive frontend, PHP backend logic, MySQL persistence, user sessions, CRUD operations, map integration, data validation, and an administrative workflow.

Core Design Principle

Public information should remain easy to access, while contribution and management functions must be controlled through authentication and authorization.

Users, Roles, and Permissions

QuenchMap separates public access, community contribution, and administrative management into distinct roles.

Public Access

Guest

Can view the map, search locations by city, inspect public water-source information, and read published announcements without creating an account.

Authenticated Access

Registered User

Receives the public functions and can additionally submit a new water-source report with location and descriptive data.

Management Access

Administrator

Manages reports, locations, users, and public announcements, preserving the structure and operational control of the platform.

The system combines discovery, contribution, administration, and persistent storage within one web application.

City-Based Search

Location Reporting

Public Announcements

Interactive Map Integration

The map is the primary discovery interface of QuenchMap. Geographic coordinates stored in the database are translated into visible markers on the map.

Each marker represents a water-source record and can be associated with descriptive information relevant to the user. This connects structured database content with an intuitive geographic view.

City-based search helps narrow the geographic context and makes the system more usable than an unfiltered list of coordinates or database records.

Integration Value

The external mapping service is not treated as a decorative component. It acts as the visual layer through which database records become geographically meaningful.

Database Design

MySQL provides persistent storage for the entities required by the platform. The database separates identity, geographic content, user contribution, and administrative communication.

Entity Purpose Typical Relationships
Users Stores account information and application role. Connected to authentication and user-submitted reports.
Water Sources / Locations Stores the geographic and descriptive data displayed on the map. Connected to city search and map markers.
Reports Preserves data submitted through the contribution workflow. Connected to registered users and administrative actions.
Announcements Stores public messages created through the administrative interface. Displayed to guests and authenticated users.

The public portfolio description focuses on the logical data model rather than exposing deployment credentials or environment-specific configuration.

Authentication and Authorization

Authentication identifies the user, while authorization determines which functions the authenticated account may access.

Public map browsing remains available without login. Contribution functions are restricted to registered users, and administrative functions are reserved for administrator accounts.

PHP sessions preserve the authenticated state across protected pages, while role checks prevent users from reaching functions outside their assigned level.

Access-Control Principle

The interface may hide restricted actions, but access control must also be enforced by server-side PHP logic. Visual restriction alone is not authorization.

Administrative Management

The administrative dashboard centralizes the operations that should not be exposed to ordinary users.

Location and Report Management

Administrators can inspect and manage the records that feed the public map and location-search experience.

User Management

The platform provides controlled access to account-related information required for operational administration.

Announcement Management

Administrators can create and maintain public notices shown through the application.

Centralized CRUD Workflow

Create, read, update, and delete operations are grouped in a restricted environment rather than scattered across public pages.

Application Architecture

QuenchMap separates presentation, request handling, access control, database interaction, and external map visualization into logical layers.

Presentation Layer

Bootstrap layouts, forms, navigation, public pages, and dashboard screens.

Application Layer

PHP request processing, form handling, page logic, and CRUD operations.

Access Layer

Login, sessions, role checks, and protected routes.

Data Layer

MySQL persistence for users, reports, locations, and announcements.

Map Integration Layer

Geographic visualization, marker placement, and location-search context.

Application Workflow

A guest begins with public information and geographic search. When the user decides to contribute, authentication introduces a controlled transition from public access to data submission.

Submitted data enters the persistent database and becomes manageable through the administrator interface. Public-facing pages then retrieve the relevant records and transform them into map markers, search results, and announcements.

This workflow connects public discovery, authenticated contribution, persistent storage, and administrative control without mixing the responsibilities of the three user roles.

System Flow

Public access → authentication → structured report → database persistence → administrative management → geographic presentation.

Testing and Validation

The application was tested through role-based scenarios, database operations, form validation, and map-related interactions.

Guest Access

Public users were tested against map viewing, city search, announcements, and restricted-page access.

Registration and Login

Valid, invalid, incomplete, and duplicate account scenarios were used to examine authentication behavior.

Role Authorization

Registered users and administrators were tested against functions outside and inside their assigned access level.

Report Validation

Missing values, malformed inputs, and complete submissions were tested before database persistence.

CRUD Operations

Create, read, update, and delete workflows were tested across the administrative interface.

Map and Search Behavior

Stored coordinates, marker rendering, and city-based search were checked against database records.

Key Engineering Decisions

Role Separation

Guest, user, and administrator functions were separated to prevent public access from being confused with contribution or management rights.

Database-Driven Map Content

Markers are derived from persistent records rather than being hard-coded into the interface.

Centralized Administration

Restricted operations are grouped in one dashboard to improve clarity and maintainability.

Public-First Experience

Users do not need an account merely to access the practical information for which the platform exists.

Project Outcome

The result is a functional full-stack prototype that connects geographic data, user accounts, community reports, administrative management, and public information.

The project demonstrates practical integration of frontend presentation, PHP backend logic, MySQL persistence, CRUD operations, user sessions, role-based authorization, and an external mapping service.

QuenchMap is therefore not simply a website containing a map. It is a structured information system in which map content is produced, stored, controlled, and presented through a defined user workflow.

Why This Project Matters

It shows the ability to design and implement a complete user-facing web system with data persistence, access control, geographic visualization, and operational administration.

Project Strengths

  • Full-stack PHP and MySQL implementation.
  • Interactive geographic visualization.
  • Guest, user, and administrator roles.
  • Structured location-reporting workflow.
  • Centralized CRUD administration.
  • City-based search and public announcements.
  • Responsive Bootstrap interface.

Current Limitations

  • The project is a functional academic prototype rather than a production public service.
  • The quality of geographic data depends on user input and administrative maintenance.
  • External map functionality depends on service availability and deployment configuration.
  • The current system does not include automated field verification of reported water sources.
  • Advanced moderation, audit history, and notification systems are outside the current scope.

Future Development

The prototype provides a base for a more complete public location-information platform.

  • Administrative approval states for submitted reports.
  • User photographs and source-condition updates.
  • Duplicate-location detection.
  • User ratings and confirmation history.
  • Map filters for status, city, and source type.
  • Email or in-application notifications.
  • Audit logs for administrative actions.
  • Improved security controls and production deployment.
  • Mobile-first location submission.
  • Multilingual public interface.
