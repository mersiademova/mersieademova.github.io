Meal Demand Decision Support System

Python · PyQt6 · Streamlit · SQLite · Statistical Forecasting · Data Visualization

Case Study

From a real operational planning problem to a desktop and browser-accessible predictive system.

The project was originally developed as a PyQt6 desktop application for a real organizational catering workflow. A Streamlit interface was later added to make the dashboard, historical demand, forecasting methods, model comparison, and public demonstration data directly accessible through a browser.

The Problem

Meal planning in large organizational catering environments often depends on manually collected attendance information, previous experience, and short-term estimates.

These methods may not sufficiently account for historical demand patterns, menu structure, category preferences, working-day conditions, changes in actual attendance, and unexpected operational circumstances.

Inaccurate estimates can result in food waste, shortages, unnecessary operational costs, and unreliable planning. The challenge is therefore not limited to calculating a number. It requires the complete planning context to be collected, structured, preserved, and evaluated.

Project Motivation

The project originated from observing a real operational planning problem: the number of meals that must be prepared changes according to attendance, menu composition, meal category, working-day type, and previous demand patterns.

From Isolated Calculation to Complete System

Instead of treating prediction as an isolated statistical calculation, I designed a complete application that connects menu planning, historical records, prediction, realized demand, accuracy analysis, and reporting within one structured workflow.

Project Objective

The objective was to develop a structured decision-support system capable of transforming historical operational data into measurable, reviewable, and comparable meal-demand forecasts.

The system preserves the planning context, compares forecasts with realized demand, evaluates model accuracy, and presents the same analytical logic through both a PyQt6 desktop application and a Streamlit web interface.

Core Functionalities

The application integrates the complete operational and analytical cycle instead of treating each activity as an unrelated process.

Weekly Menu Management

Creates and manages one menu for each calendar week. Working days, weekends, holidays, and non-working days can be defined, while meals are organized by standard categories.

Historical Data Management

Preserves previous demand records for comparing similar periods, recognizing recurring patterns, and preparing structured input data for prediction models.

Prediction Module

Evaluates historical demand in relation to menu categories, previous observations, and operational context to generate an estimated demand for the selected planning period.

Realized Demand Entry

Allows the user to record the demand that actually occurred, creating a measurable connection between forecast values and real operational results.

Accuracy Evaluation

Compares predicted and realized demand, calculates deviations, and tracks model accuracy so that every forecast can be reviewed instead of accepted without verification.

Reports and Visual Analysis

Generates statistical summaries, prediction-versus-reality comparisons, historical analyses, graphical reports, and visual accuracy indicators.

Browser-Accessible Analysis

A Streamlit interface provides direct access to the dashboard, weekly menus, historical demand, forecasting, method comparison, packages, codebooks, and interactive visual analysis.

Database Persistence

Menus, categories, calendar periods, historical demand, generated predictions, realized quantities, and analytical results are stored in a structured database rather than being kept only temporarily during application execution.

Statistical Approach

The forecasting layer implements seven methods: arithmetic mean, median, moving average, weighted moving average, linear trend, exponential smoothing, and a combined method that aggregates several estimates.

Each forecast includes descriptive statistics and a 95% confidence interval. Rolling evaluation compares predictions with later observed values using MAE, MAPE, and RMSE so that model performance remains measurable rather than assumed.

Measurable Prediction

A useful prediction must be testable. By entering realized demand and comparing it with the forecast, the application transforms prediction from an unsupported assumption into a measurable experiment.

System Architecture

The system is divided into logical layers that separate two presentation interfaces, operational logic, forecasting services, persistent SQLite data, and analytical reporting.

Presentation Layer

PyQt6 desktop interface and Streamlit web interface.

Application Logic

Menu, demand, calendar, and workflow management.

Statistical Layer

Prediction, parameter estimation, and evaluation methods.

Data Layer

Relational database and structured historical records.

Reporting Layer

Interactive tables, statistical summaries, Matplotlib charts, and Streamlit visualizations.

Application Workflow

The user follows a structured process from menu creation to final evaluation. Each completed cycle produces new historical information for future predictions.

1

Select the Planning Week

The user selects an existing week or creates a new calendar period.

2

Define Day Types

Working days, weekends, holidays, and non-working days are identified.

3

Create the Weekly Menu

Meal packages and standard categories are assigned to each relevant day.

4

Connect Historical Data

The system relates the new planning context to previous operational records.

5

Generate Prediction

The selected statistical model produces an estimated demand.

6

Enter Realized Demand

Actual quantities are recorded after the operational period.

7

Evaluate Accuracy

Deviations and prediction accuracy are calculated and displayed.

8

Preserve the Results

Final results become part of the historical database for future analysis.

Key Engineering Decisions

The architecture and implementation choices were based on the intended operational environment, the need for traceable data, and the requirement that every forecast remain reviewable.

Why Desktop and Browser Interfaces?

The PyQt6 application supports controlled local operational use, while the Streamlit interface provides a portable browser-accessible demonstration of the same forecasting logic and analytical workflow.

Why a Structured Database?

A predictive system has limited value without a consistent historical record. The database preserves the relationship between menus, demand, forecasts, realized values, and evaluation results.

Why Connect Prediction to Menus?

Demand does not depend only on total attendance. It can also be influenced by the composition, category, and perceived attractiveness of the available meal options.

Why Include Accuracy Analysis?

A prediction should not only be generated. It must be compared with reality so that the model can be understood, evaluated, and improved over time.

Testing and Evaluation

The application was tested as a connected workflow across the desktop and web interfaces: data loading, weekly-menu inspection, historical-demand filtering, forecast generation, confidence intervals, model comparison, database access, and visual reporting.

Particular attention was given to consistent read-only access to the public demonstration database, repeatable forecast calculations, model evaluation through MAE/MAPE/RMSE, and clear separation between interface code and statistical services.

Evaluation Principle

Prediction quality must be assessed through repeated comparison with real outcomes. The system therefore preserves both the forecast and the realized demand instead of replacing one value with the other.

Project Outcome

The result is a functional decision-support system with two interfaces: a PyQt6 desktop application for the complete local workflow and a Streamlit web application for browser-accessible exploration and demonstration.

The project demonstrates how a real operational problem can be transformed into a layered software and data system while preserving a clear connection between domain knowledge, statistical methodology, measurable evaluation, and responsible public presentation.

Why This Project Matters

The project is not based on a tutorial, an isolated algorithm, or an artificial exercise. It begins with a real process and develops the complete system required to analyze, support, test, and improve that process.

Project Strengths

  • Originates from an observed real-world operational problem.
  • Models the complete process before and after prediction.
  • Combines software development, databases, statistics, interface design, operational analysis, and documentation.
  • Includes a measurable mechanism for evaluating predictions.
  • Supports iterative development and future enterprise integration.
  • Provides both desktop and browser-accessible interfaces without duplicating the forecasting logic.
  • Publishes a protected demonstration dataset while keeping the original workplace database private.

Current Limitations

  • The system has not yet been integrated with a live enterprise data source.
  • Some operational information still requires manual entry in the desktop workflow.
  • Forecast quality depends on the volume, consistency, and relevance of historical records.
  • Unexpected attendance changes, menu substitutions, and organizational events may influence results.
  • The public web version is a demonstration environment and does not provide authenticated multi-user editing.

Future Development

The current prototype establishes the system architecture and analytical workflow. Future development can focus on automation, integration, broader deployment, and continuous model improvement.

  • Automated import and export of operational data.
  • API integration with an organizational information system.
  • Automated attendance-data retrieval.
  • Additional predictive models and automatic model selection.
  • Authenticated multi-user deployment with role-based access.
  • Multiple organizational sites and centralized reporting.
  • Interactive deviation alerts and threshold-based notifications.
  • Cost, food-waste, and shortage analysis.
  • Long-term model monitoring and retraining rules.
  • Integration with a hardware-based operational tracking system.

Public Demonstration Data

The system was developed around a real workplace meal-planning process and historical operational records. The original database is not published.

What the public version preserves

The demonstration database keeps the relational structure, realistic menu descriptions, workflow relationships, and broad statistical behavior needed to test the application meaningfully.

Company identifiers are generic, while dates and demand quantities are anonymized or modified. This allows the desktop and Streamlit versions to remain fully demonstrable without exposing confidential operational records.
